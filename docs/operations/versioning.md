# バージョン付番ルール

## 1. 適用範囲と基本方針

この文書は ComfyUI Batch Studio のバージョン付番に関するプロジェクト内の正本である。以下はプロジェクトの運用方針として定め、業界全体の統一規格とは扱わない。アプリのリリース番号は `MAJOR.MINOR.PATCH`、Git タグは `vMAJOR.MINOR.PATCH` とする。各桁は非負整数で、先頭ゼロを付けない。`v` はタグ名の接頭辞であり、バージョン値には含めない。

番号は変更量・コミット数・PR 番号・作業日ではなく、利用者に届く機能と互換性への影響で決める。一つのリリースに複数の変更が含まれる場合は、最も大きい付番区分を一度だけ適用する。MINOR 更新では PATCH を、MAJOR 更新では MINOR と PATCH を `0` に戻す。

通常の機能実装、修正、リファクタリング、テスト追加、文書更新ではアプリ番号を更新しない。リリース準備として明示された作業で更新する。付番ルールの策定・修正自体もリリースの指示とは扱わない。

付番の判断は本書に従う。配布ツールのバージョン形式・比較方法に関する制約も満たす。番号の形式と、変更内容に応じた増分の判断は区別する。

## 2. 付番の判断

### 2.1 開発段階の `0.x.y`（`0.0.y` を含む）

`0.x.y` の x を機能版（MINOR）、y を修正版（PATCH）として使う。会話や説明の `0.x` は機能系列の略称であり、実際の保存値・タグは `0.x.0` のように三桁で記載する。

| 変更 | 更新する桁 | 例 |
| --- | --- | --- |
| バグ修正、セキュリティ修正、互換性を保つ性能・UI 改善、内部整理・依存関係の保守 | y（PATCH）を一つ増やす | `0.0.3` → `0.0.4`、`0.79.0` → `0.79.1` |
| 機能追加・機能拡張、新しい工程・操作・連携、非推奨化、互換性のない変更 | x（MINOR）を一つ増やし、y を `0` に戻す | `0.0.3` → `0.1.0`、`0.79.1` → `0.80.0` |
| 安定版への移行 | 利用・連携契約と対応範囲を明示し、その検証を完了して `1.0.0` とする | 桁数やリリース回数では決めない |

機能追加とバグ修正をまとめてリリースする場合は x を増やし、y を `0` に戻す。変更の目的と利用者への実際の影響で判断し、改善という名称でも新しい能力を追加するなら x を増やす。UI の誤字・表示崩れの修正は y、新しい操作の追加は x とする。内部整理・依存更新でも互換性を失うなら x を増やす。文書・テストだけの変更は原則として単独リリースを要しない。

`0.0.y` にも同じ判断基準を適用し、新機能・破壊的変更を試作回数として PATCH にまとめない。修正の継続なら `0.0.9` → `0.0.10` とする。既存系列を `0.0.y` に戻さない。開発段階であることと、破壊的変更の影響・移行方法を付番時の完了報告に明記する。

### 2.2 安定版の `1.0.0` 以降

安定版では、以下のプロジェクト運用により、文書化された利用・連携契約への影響を区別する。

| 区分 | 判断基準 |
| --- | --- |
| PATCH | 後方互換性を保つバグ修正・性能改善・UI 改善・内部整理・依存関係の保守 |
| MINOR | 後方互換性を保つ機能追加・機能拡張、または非推奨化 |
| MAJOR | パブリック API に対する後方互換性のない変更 |

機能追加とバグ修正を含む場合は MINOR、非互換変更も含む場合は MAJOR とする。文書・テストだけの変更は原則として単独リリースを要しない。依存更新も、利用者への機能・互換性の影響で判断する。

### 2.3 互換性の評価対象

本アプリの互換性は、利用者・外部ツールが依存する以下の文書化された契約を基準に評価する。

| 契約 | 定義を所有する文書 |
| --- | --- |
| 保存・交換するプロジェクトデータ、読込・保存・再開の契約 | [Project Artifacts](../contracts/project-artifacts.md)、[Prompt Plan](../contracts/prompt-plan.md) |
| Workflow 入出力、Template / Manifest、出力配置・命名 | [Workflow Compiler](../architecture/workflow-compiler.md) |
| 外部サービス・ツールとの入出力、必要な連携条件 | [External Tools](../integrations/external-tools.md)、[Service Integrations](../integrations/service-integrations.md)、[Remote Execution](../architecture/remote-execution.md) |
| 利用者が依存する工程操作・設定・必須環境 | [Product Scope](../product/scope-and-flow.md)、[Application Shell](../ui/application-shell.md)、[README](../../README.md) |

内部関数、Component 構成、アプリ内だけで使用する IPC は、それ自体を外部向けパブリック API とは扱わない。ただし、その変更が上記の契約に及ぼす影響は評価する。API を追加・変更する際は、対応する正本も更新する。

以下を変更前後で確認する。

- 既存プロジェクト・設定・実行履歴の読込、保存、再開。
- 工程操作、モデル選択、生成物の配置・命名、既存の連携方法。
- ComfyUI / custom node、CLI、SSH、R2 等の連携契約と必須環境。
- 既存環境では満たせなくなる Node.js / OS / 外部ツールの必須条件。

依存パッケージの MAJOR 更新を、そのままアプリの MAJOR 更新とは扱わない。アプリ利用者への実際の影響で判断する。必須環境の引き上げ、機能削除、手動移行の必須化、旧版が読めなくなる保存形式変更は、互換性のない変更として扱う。自動移行があるだけで互換性ありと判定せず、旧版への復帰可否も記録する。

## 3. 番号の正本と独立したバージョン

| 対象 | 正本・更新対象 | 更新判断 |
| --- | --- | --- |
| アプリ | `package.json` の `version`。`package-lock.json` のトップレベル `version` と `packages[""].version` を同期 | アプリのリリース全体に対して第 2 節を適用 |
| 保存形式 | 各契約の `schemaVersion`、対応する Schema・validator・migration | 当該形式の契約変更時に、その契約の規則に従う |
| Workflow Template / Manifest | Template の `version`、Manifest の `manifestVersion` と Template binding | [Workflow Compiler 設計](../architecture/workflow-compiler.md)に従い、Template hash も整合させる |
| Workflow Compiler | `src/main/compiler.ts` の `compilerVersion` | コンパイル結果・解釈・検証の意味が変わる際に独立して更新。互換性を保つ修正は PATCH、機能追加は MINOR、互換性のない変更は MAJOR |
| Remote Worker | `src/main/remote-worker-source.ts` 内の Worker バージョン | Worker の挙動・プロトコル変更時に、Main Process 側との整合性を確認して既存形式で更新 |

アプリのリリースだけを理由に、これらの独立した番号を一括更新しない。逆に、通常の実装でも当該契約や Compiler 等の変更に必要な番号更新は行う。`schemaVersion` が整数の形式にアプリの三桁番号を入れない。テスト用の過去バージョンや移行 fixture も機械的に置換しない。

## 4. リリース準備の手順

1. 作業ツリーの変更、対象ブランチ、ローカルとリモートのタグ、直前のリリース内容を確認する。リモートへアクセスできる場合は最新情報を取得する。確認できない場合は番号を候補として報告し、未確認のままタグや公開リリースを作らない。
2. 対象リリース系列の最新リリースを基準に、未リリースの変更全体を分類する。最新系列の次番号は既存番号より大きくする。過去系列の修正を明示された場合は、その系列の最新 PATCH を基準にし、後続系列への修正反映も確認する。
3. 作業ツリーと対象ブランチ・タグの番号が異なる場合は、古いブランチ、リリース準備中、別系列のどれかを確認する。番号だけを上書きして不一致を隠さない。
4. `package.json` と lockfile の三箇所を同期する。`npm version <次の番号> --no-git-tag-version` を利用できるが、実行前に npm lifecycle scripts を確認する。手編集でも同じ整合性を満たす。依存パッケージ自身の番号を変更しない。
5. [エージェント向けルールのリリースノート形式](../../AGENTS.md#リリースノートの形式)に従い、対象範囲のPRタイトル・PRリンクと `Full Changelog` で GitHub Release 本文を準備する。リリースノートの正本は GitHub Release 本文とし、`docs/` には保存しない。CLI用の本文は一時ファイルで扱う。互換性・移行への影響と検証結果は付番判断・完了報告で確認し、リリース本文には説明を追加しない。
6. 差分を確認して、対象コミットについて `.github/workflows/ci.yml` の現行チェックを満たす。現行 CI は整形・Lint、型チェック、回帰テスト、ビルド、画像メモリ検証を含む。Linux / GUI 専用検証は対応する CI で確認し、ローカルのスキップを成功の根拠にしない。
7. 公開を含む依頼である場合は、検証済みコミットにアプリ番号と一致するタグを付け、リリースノートと対応させる。番号更新だけの依頼から push・タグ公開・GitHub Release 作成までを推定しない。

既に公開した番号の内容やタグの参照先は変更しない。公開後に修正が必要なら新しい番号を発行する。複数のリリース準備が並行した場合は、公開直前に最新タグと重複を再確認し、競合した候補番号を更新する。

## 5. プレリリース・ビルドメタデータ・比較

通常は三桁のリリース番号を使用する。プレリリースが明示的に必要な場合だけ、`0.80.0-alpha.1`、`0.80.0-beta.1`、`0.80.0-rc.1` の形式を使う。タグにも `v` を付ける。同一段階の修正では末尾の整数を増やし、正式版では接尾辞を外す。正式版の公開後に同じ基本番号のプレリリースを追加しない。

識別子は空でない ASCII 英数字・ハイフンをドットで区切る。プレリリースの数値識別子に先頭ゼロを付けない（`rc.01` は不可）。ビルドメタデータは `+` で追加できる（例：`1.2.3+sha.abc123`）。ビルドメタデータの数値識別子には先頭ゼロを使えるが、優先順位には影響しない。公開済み内容を差し替えるためにメタデータだけを変えない。

配布ツールと整合するよう、比較には次の優先順位を使う。三桁と数値のプレリリース識別子は数値として、非数値識別子は ASCII 順で比較し、数値識別子を非数値より低く扱う。同じ識別子列の接頭部分が一致する場合は、識別子の多い側を高く扱う。同じ三桁ではプレリリースより正式版が高い。例：`1.0.0-alpha.1 < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0`。`1.0.0+build.1` と `1.0.0+build.2` は同じ優先順位とする。タグの単純な文字列順で最新バージョンを判定しない。

開発中の各コミットを識別するためにアプリ番号を増やさない。コミット SHA を利用する。プレリリースを公開する場合は、配布・表示・更新判定が接尾辞を扱えることを検証する。

## 6. エージェントの完了報告

付番した場合は、旧番号 → 新番号、PATCH / MINOR / MAJOR の判断理由、互換性と移行への影響、更新ファイル、実施した検証、未確認事項を簡潔に報告する。付番しなかった場合は、通常変更かルール策定であることを必要に応じて説明する。
